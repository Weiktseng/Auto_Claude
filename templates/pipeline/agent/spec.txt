# <專案名稱> — 規格書

> **編號系統**：`<類別>-<領域>-<序號>` 例如 `FR-CHAT-01`
>
> | 類別前綴 | 全稱 | 用途 |
> |---|---|---|
> | `FR-` | Functional Requirement | 功能需求（系統要做什麼） |
> | `NFR-` | Non-Functional Requirement | 非功能需求（效能、安全、可用性、部署） |
> | `OOS-` | Out of Scope | 明確不做的東西 |
>
> | 常用領域代碼 | 意思 | 範例 |
> |---|---|---|
> | `AUTH` | 認證/授權 | FR-AUTH-01 使用者能登入 |
> | `CHAT` | 對話/訊息 | FR-CHAT-03 對話歷史保留 |
> | `DAT` | 資料/儲存 | FR-DAT-01 匯出 CSV |
> | `UI` | 使用者介面 | FR-UI-02 RWD 支援手機 |
> | `API` | 對外 API | FR-API-01 REST endpoint |
> | `INT` | 整合/串接 | FR-INT-01 串接第三方 OAuth |
> | `RPT` | 報表/統計 | FR-RPT-01 每日活躍使用者 |
> | `SEC` | 安全 | NFR-SEC-01 密碼用 bcrypt |
> | `PERF` | 效能 | NFR-PERF-01 API < 500ms |
> | `REL` | 可靠性 | NFR-REL-01 99.9% uptime |
> | `DEP` | 部署/環境 | NFR-DEP-01 Docker 容器化 |
> | `TST` | 測試 | NFR-TST-01 覆蓋率 > 80% |
>
> **領域代碼是自訂的**，上表只是常用建議。專案有特殊領域就自己加（例如 `FR-VET-01` 獸醫、`FR-SRT-01` 字幕）。
>
> **優先級**：每條需求後面標 `[P0]` / `[P1]` / `[P2]`
> - P0 = 不做就不能 demo
> - P1 = demo 能過但缺了會被問
> - P2 = 有很好、沒有不影響交付
> - Dev 按 P0 → P1 → P2 順序做
>
> **細分**：子需求用 `.N` 接續，例如 `FR-CHAT-02.1`、`FR-CHAT-02.2`
> - 隨時可拆，不用一開始就展開到最細
> - 子需求繼承或降低父級優先級，不可升高
>
> **本檔案是客戶/PM 的原始契約，Phase 切分策略寫在 context.md，不要改這裡。**

## Phase 1 硬鎖定檢查（切 phase 時對照此表）

以下類別的需求如果被排到 Phase 2+，代表 phase 邊界畫錯了 — 移回 Phase 1 或重切。
Phase 2+ 的所有需求必須只 append 新東西（新表 / 新 endpoint / 新頁面），不修改 Phase 1 的 schema 或 API。

| 類別 | 為什麼必須 Phase 1 定 | Phase 2 才改的代價 |
|---|---|---|
| **NFR-DEP** 技術棧選型 | 語言、框架、DB、runtime。寫完 3000 行就不能換 | 重寫 |
| **FR-DAT** 核心 data model | 主表 schema、主鍵、table relation。Phase 2 可以加新表新欄位，但改既有欄位名或 relation 方向要 migrate 全部資料 | Migration 地獄 + 舊 API 全改 |
| **FR-API** API 契約格式 | URL pattern、error format、pagination schema。前端或第三方一旦開始串接就不能改 | 版本分裂，前後端同時改 |
| **NFR-SEC** 認證架構 | 認證 pattern（JWT / session）、租戶模型（single / multi）、權限模型（RBAC / ABAC）。不是每條安全規則，是架構級的選擇 | 每支 endpoint 都要加 auth middleware |

### 軟鎖定（Phase 1 最好定，Phase 2 能改但痛苦）

| 類別 | 為什麼建議 Phase 1 | 不做的代價 |
|---|---|---|
| **FR-AUTH** 使用者模型 | user 表結構、有沒有 role、單/多租戶 | 後加 multi-tenant 要在所有 query 加 filter |
| **NFR-DEP** 部署方式 | Docker vs bare metal、port、config 載入方式 | 本機能跑但部署時路徑問題一堆 |
| **FR-DAT** 檔案儲存策略 | local filesystem vs S3 vs DB blob | Phase 2 搬遷資料 + 改讀取路徑 |

### 不鎖（Phase 2+ 再做沒事）

| 類別 | 為什麼可以後做 |
|---|---|
| **FR-UI** 介面美化 / RWD | CSS 隨時改，不影響 backend |
| **FR-RPT** 報表統計 | 純讀取，data model 正確就能 append |
| **NFR-PERF** 效能調校 | 先正確再快，index 隨時加 |
| **FR-INT** 第三方串接 | API 契約穩定的話，串接是 adapter 問題 |
| **所有 P2** | 定義上就是「沒有不影響交付」 |
